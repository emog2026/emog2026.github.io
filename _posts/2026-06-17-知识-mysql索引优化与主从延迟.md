# 📌 一句话总结
索引让查询飞快，主从延迟处理保证数据实时同步

## 🎯 这是什么？

### 基础定义
**MySQL 索引优化**：通过创建合适的索引结构，大幅提升查询性能的技术。

**主从延迟处理**：解决主从复制中从库落后于主库的时间差问题，保证数据一致性。

### 通俗类比

**索引优化**：
想象一本没有目录的书 vs 有目录的书：
- **无索引**：找某个名字要翻遍整本书（全表扫描）
- **有索引**：查目录直接翻到对应页（索引查找）

**主从延迟**：
想象直播看球赛：
- **无延迟**：现场和电视同步（同步复制）
- **有延迟**：电视比现场慢 5 秒（异步复制延迟）
- **处理方案**：加快转播速度或读实时比分（优化策略）

### 为什么存在

**索引优化解决**：
- 查询慢：全表扫描耗时长
- CPU 负载高：扫描大量无用数据
- 并发低：锁等待时间长

**主从延迟解决**：
- 读写分离读到旧数据
- 数据不一致
- 从库压力过大
- 网络传输慢

## 🏗️ 核心原理

### 索引工作原理

```
┌─────────────────────────────────────────────────────────┐
│                   B+Tree 索引结构                         │
├─────────────────────────────────────────────────────────┤
│                                                         │
│                      [Root]                              │
│                    100 | 200 | 300                       │
│                   /    |    \                           │
│              ┌────┐ ┌────┐ ┌────┐                       │
│              [50] [150] [250] [350]                      │
│             /  \   /  \   /  \   /  \                     │
│          [10][40][120][180][220][280][320][380]           │
│          / \   / \   / \   / \   / \   / \   / \           │
│        [5][15][35][45][110][130][170][190]...             │
│                                                         │
└─────────────────────────────────────────────────────────┘

查询 id = 150：
1. 从 Root 开始：150 在 100-200 之间
2. 走到第二层 [150]
3. 继续查找：找到 150
时间复杂度：O(log n)，相比全表扫描 O(n) 快得多
```

### 索引类型

| 索引类型 | 说明 | 适用场景 |
|----------|------|----------|
| **主键索引** | 聚集索引，数据按主键存储 | 主键、唯一 ID |
| **唯一索引** | 值唯一，允许 NULL | 手机号、身份证 |
| **普通索引** | 基本索引，无唯一约束 | 常用查询字段 |
| **联合索引** | 多个字段组合索引 | 多条件查询 |
| **全文索引** | 对文本内容搜索 | 文章搜索（5.6+） |
| **哈希索引** | Memory 引擎使用 | 精确匹配查询 |

### 主从延迟原理

```
┌─────────────────────────────────────────────────────────┐
│                      主从复制延迟                           │
├─────────────────────────────────────────────────────────┤
│                                                         │
│  Master                    Slave                        │
│  (主库)                     (从库)                       │
│                                                         │
│  ┌──────────┐   binlog    ┌──────────┐                 │
│  │写入数据   │────────────>│IO线程读取 │ 100ms          │
│  │(1ms)     │   网络延迟   │(100ms)   │ 网络延迟         │
│  └──────────┘             └──────────┘                 │
│                                  │                       │
│                                  │relay log             │
│                                  ▼                       │
│                           ┌──────────┐                  │
│                           │SQL线程   │ 500ms           │
│                           │重放SQL   │ 执行慢           │
│                           │(500ms)   │                  │
│                           └──────────┘                  │
│                                                         │
│  总延迟 ≈ 1ms + 100ms + 500ms = 601ms                   │
│  Seconds_Behind_Master = 0.6                           │
└─────────────────────────────────────────────────────────┘
```

### 延迟来源分析

| 延迟来源 | 占比 | 原因 | 优化方向 |
|----------|------|------|----------|
| 网络延迟 | 20% | 主从距离远、带宽小 | 优化网络、压缩传输 |
| IO 线程慢 | 10% | 磁盘写 relay log 慢 | SSD、批量写入 |
| SQL 线程慢 | 60% | 从库执行慢 | 并行复制、优化查询 |
| 锁等待 | 10% | 从库有长查询 | read-only、kill 查询 |

## 💼 应用场景

### 场景 1：索引优化 - 电商订单查询加速

**痛点**：
```sql
-- 查询某用户的订单，耗时 5 秒
SELECT * FROM orders
WHERE user_id = 12345
AND created_at >= '2024-01-01'
ORDER BY created_at DESC
LIMIT 20;
```

**分析**：
- `orders` 表有 1000 万行
- 无索引，全表扫描
- 每次查询扫描 1000 万行

**优化方案**：

```sql
-- 1. 创建联合索引
CREATE INDEX idx_user_created ON orders(user_id, created_at);

-- 2. 验证索引使用
EXPLAIN SELECT * FROM orders
WHERE user_id = 12345
AND created_at >= '2024-01-01'
ORDER BY created_at DESC
LIMIT 20\G

-- 关键字段：
-- type: ref（索引查找）
-- key: idx_user_created（使用的索引）
-- rows: 150（扫描行数，从 1000 万降到 150）

-- 3. 查询耗时从 5 秒降到 0.01 秒
```

**效果**：
- 查询速度提升 500 倍
- CPU 使用率降低 90%
- 并发能力提升 10 倍

**痛点**：
```sql
-- 用户搜索商品，LIKE 导致全表扫描

-- 扫描 50 万行，耗时 3 秒
```

```sql
-- 方案 1：前缀匹配（推荐）

WHERE name LIKE '手机%';
-- 使用索引，耗时 0.02 秒

-- 方案 2：全文索引（MySQL 5.6+）
CREATE FULLTEXT INDEX idx_name_fulltext ON products(name);

-- 使用全文搜索
SELECT * FROM products
WHERE MATCH(name) AGAINST('手机' IN NATURAL LANGUAGE MODE);
-- 耗时 0.05 秒

-- 方案 3：Elasticsearch（大量数据）
-- 将数据同步到 ES，使用 ES 搜索
```

**效果**：
- 搜索速度提升 60 倍
- 用户体验显著改善

### 场景 3：主从延迟处理 - 并行复制

**痛点**：
```sql
-- 从库延迟持续 10-30 秒
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: 25
-- 原因：从库单线程重放，主库写入太快
```

**优化方案**：

```ini
# 从库 my.cnf 开启并行复制
[mysqld]
# MySQL 5.7+ 并行复制配置
slave_parallel_type = LOGICAL_CLOCK
slave_parallel_workers = 4  # 根据 CPU 核心数调整
slave_preserve_commit_order = ON  # 保持事务顺序
slave_pending_jobs_size_max = 128M

# MySQL 8.0+ 写入集并行复制（更智能）
slave_parallel_type = WRITESET
```

```sql
-- 重启从库后验证
SHOW VARIABLES LIKE 'slave_parallel%';

-- 停止并重启复制
STOP SLAVE;
START SLAVE;

-- 监控延迟
SHOW SLAVE STATUS\G
-- Seconds_Behind_Master: 0 或 1-2 秒
```

**效果**：
- 延迟从 25 秒降到 1-2 秒
- 4 线程并行重放 SQL
- 充分利用多核 CPU

### 场景 4：主从延迟处理 - 读写分离路由策略

**痛点**：
```
用户下单后立即查询订单，读到了旧数据
主库：订单已创建
从库：还没同步该订单
用户：看到"订单不存在"，困惑
```

**优化方案**：

**方案 1：强制写后读主库（推荐）**

```python
# Python 应用代码
import redis

class MySQLRouter:
    def __init__(self):
        self.redis_client = redis.Redis()
        self.master_db = self.connect_master()
        self.slave_db = self.connect_slave()

    def write(self, sql, params=None):
        """写操作走主库"""
        result = self.master_db.execute(sql, params)

        # 写操作后，标记该用户 5 秒内读主库
        user_id = self.get_current_user_id()
        self.redis_client.setex(
            f"read_master:{user_id}",
            5,  # 5 秒内读主库
            "1"
        )
        return result

    def read(self, sql, params=None):
        """读操作根据标记决定读主库还是从库"""
        user_id = self.get_current_user_id()

        # 检查是否需要读主库
        if self.redis_client.exists(f"read_master:{user_id}"):
            return self.master_db.execute(sql, params)

        # 正常读从库
        return self.slave_db.execute(sql, params)

# 使用示例
router = MySQLRouter()

# 写操作
router.write("INSERT INTO orders ...")

# 立即查询，会读主库，确保数据一致性
router.read("SELECT * FROM orders WHERE id = ?", [order_id])
```

**方案 2：监控延迟动态路由**

```python
class SmartMySQLRouter:
    def __init__(self, max_delay=2):
        self.master_db = self.connect_master()
        self.slave_db = self.connect_slave()
        self.max_delay = max_delay

    def get_slave_delay(self):
        """获取从库延迟"""
        result = self.slave_db.query(
            "SHOW SLAVE STATUS"
        ).fetchone()

        delay = result.get('Seconds_Behind_Master', 0)
        return delay

    def read(self, sql, params=None):
        """根据延迟选择读主库还是从库"""
        delay = self.get_slave_delay()

        if delay > self.max_delay:
            # 延迟过大，读主库
            return self.master_db.execute(sql, params)

        # 延迟可接受，读从库
        return self.slave_db.execute(sql, params)
```

**方案 3：数据库中间件（推荐）**

```yaml
# ProxySQL 配置
mysql_servers:
  - name: master

```

**效果**：
- 用户写入后立即读到新数据
- 延迟不影响用户体验
- 充分利用从库分担读压力

### 场景 5：主从延迟处理 - 大事务拆分

**痛点**：
```sql
-- 大批量更新，导致从库延迟飙升
UPDATE user_scores
SET score = score + 100
WHERE created_at < '2023-01-01';
-- 影响 100 万行，执行 5 分钟
-- 从库延迟飙到 300 秒
```

**优化方案**：

**方案 1：分批处理**

```sql
-- 分批更新，每次 1 万行
CREATE PROCEDURE batch_update()
BEGIN
  DECLARE affected INT;
  SET affected = 1;

  WHILE affected > 0 DO
    -- 每次更新 1 万行
    UPDATE user_scores
    SET score = score + 100
    WHERE created_at < '2023-01-01'
    LIMIT 10000;

    SET affected = ROW_COUNT();

    -- 暂停 0.1 秒，让从库有机会追赶
    DO SLEEP(0.1);

    -- 显示进度
    SELECT CONCAT('Updated ', affected, ' rows') AS progress;
  END WHILE;
END;

-- 执行
CALL batch_update();
```

**方案 2：pt-online-schema-change（无锁表结构变更）**

```bash
# 在线修改表结构，不锁表
pt-online-schema-change \
  --alter="ADD COLUMN new_score INT" \
  --host=192.168.1.100 \
  --user=admin \
  --password=password \
  --database=mydb \
  --table=user_scores \
  --execute

# 会自动创建新表、复制数据、切换表
# 不影响主从复制
```

**方案 3：主库禁用，从库单独处理**

```sql
-- 主库临时禁止该语句产生 binlog
SET SESSION sql_log_bin = 0;

-- 执行大批量操作
UPDATE user_scores SET score = score + 100 WHERE ...;

-- 恢复 binlog
SET SESSION sql_log_bin = 1;

-- 单独同步到从库
mysqldump --single-transaction --where="created_at < '2023-01-01'" \
  user_scores | mysql -h slave_host user_scores
```

**效果**：
- 从库延迟从 300 秒降到 < 5 秒
- 用户几乎无感知
- 主从保持健康状态

### 场景 6：索引优化 - 覆盖索引避免回表

**痛点**：
```sql
-- 查询只需要部分字段，却扫描整行
SELECT id, user_id, status
FROM orders
WHERE user_id = 12345;
-- 虽然有 user_id 索引，但要回表查询 id 和 status
```

**优化方案**：

```sql
-- 创建覆盖索引（包含查询所需的所有字段）
CREATE INDEX idx_user_cover ON orders(user_id, id, status);

-- 验证
EXPLAIN SELECT id, user_id, status FROM orders WHERE user_id = 12345\G

-- Extra: Using index（使用覆盖索引，无需回表）
-- 耗时进一步降低 50%

-- 对比：
-- 普通索引：先查索引找到主键，再回表查完整行（2 次 IO）
-- 覆盖索引：索引包含所有需要字段，无需回表（1 次 IO）
```

**效果**：
- 查询速度再提升 50%
- 减少磁盘 IO
- 降低 CPU 消耗

## 🔍 实战检查清单

### 索引优化检查清单

**1. 识别慢查询**
```sql
-- 开启慢查询日志
SET GLOBAL slow_query_log = ON;
SET GLOBAL long_query_time = 1;  -- 1 秒以上算慢

-- 查看慢查询
SELECT * FROM mysql.slow_log
ORDER BY query_time DESC
LIMIT 10;
```

**2. 分析执行计划**
```sql
EXPLAIN SELECT ...;

-- 关注字段：
-- type: ALL（全表扫描，需要优化）
-- key: NULL（没用索引，需要添加）
-- rows: 扫描行数（越小越好）
-- Extra: Using filesort（需要优化排序）
```

**3. 检查索引使用情况**
```sql
-- 查看表索引
SHOW INDEX FROM table_name;

-- 查看索引基数
SELECT
    table_name,
    index_name,
    cardinality,
    seq_in_index
FROM information_schema.statistics
WHERE table_schema = 'your_db';
```

**4. 避免索引失效**
```sql
-- ❌ 错误：索引列使用函数
SELECT * FROM orders WHERE YEAR(created_at) = 2024;

-- ✅ 正确：改写查询
SELECT * FROM orders
WHERE created_at >= '2024-01-01'
AND created_at < '2025-01-01';

-- ❌ 错误：隐式转换
SELECT * FROM users WHERE phone = 13800138000;  -- phone 是字符串

-- ✅ 正确：使用引号
SELECT * FROM users WHERE phone = '13800138000';

-- ❌ 错误：前缀通配符
SELECT * FROM products WHERE name LIKE '%手机%';

-- ✅ 正确：前缀匹配或全文索引
SELECT * FROM products WHERE name LIKE '手机%';
```

**5. 联合索引最左前缀原则**
```sql
-- 索引：idx(a, b, c)

-- ✅ 可用索引
WHERE a = 1
WHERE a = 1 AND b = 2
WHERE a = 1 AND b = 2 AND c = 3
WHERE a = 1 AND c = 3（b 被跳过，部分使用索引）

-- ❌ 不可用索引
WHERE b = 2
WHERE c = 3
WHERE b = 2 AND c = 3
```

### 主从延迟检查清单

**1. 实时监控延迟**
```sql
-- 从库执行
SHOW SLAVE STATUS\G

-- 关键指标：
-- Slave_IO_Running: Yes（IO 线程状态）
-- Slave_SQL_Running: Yes（SQL 线程状态）
-- Seconds_Behind_Master: 延迟秒数（越低越好）
-- Last_Error: 错误信息
```

**2. 使用 pt-heartbeat 精确监控**

```bash
  --print-master-server-id
```
