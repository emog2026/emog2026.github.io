> 📚 知识关键词：CI/CD、持续集成、持续交付

📌 **一句话总结**：软件交付的"自动化流水线"，让代码从开发到生产环境全程自动化，实现快速迭代、高质量交付

---

## 🎯 这是什么？

### **基础定义**
CI/CD（Continuous Integration/Continuous Delivery or Deployment）是一套软件开发实践，通过自动化将代码的集成、测试、部署过程串联起来，实现软件的快速、频繁、可靠交付。

- **CI（持续集成）**：开发人员频繁将代码集成到共享仓库，每次集成都通过自动化构建和测试验证
- **CD（持续交付）**：代码通过测试后自动准备部署到生产环境，只需人工批准
- **CD（持续部署）**：代码通过测试后完全自动部署到生产环境，无需人工干预

### **通俗类比**
把 CI/CD 想象成"现代汽车生产线"：
- **传统开发**：像手工打造汽车——每辆车单独制造，效率低、易出错、难标准化
- **CI/CD**：像现代化流水线——零件（代码）自动传送、机器人自动检测（测试）、合格品自动出厂（部署），整个过程全程自动化

### **为什么存在**
解决软件开发的四大痛点：
1. **集成地狱**：多人开发时，合并代码经常出问题
2. **发布风险**：手动部署容易出错，回滚困难
3. **反馈缓慢**：发现问题时已经很久了，定位困难
4. **交付低效**：从开发完成到上线耗时太长

## 🏗️ 核心原理

### **它是如何工作的**

CI/CD 的核心是**流水线（Pipeline）**，典型工作流程：

```
┌─────────────────────────────────────────────────────────────┐
│                     CI/CD 工作流程                            │
├─────────────────────────────────────────────────────────────┤
│  📝 代码提交                                                 │
│     ↓                                                        │
│  🔨 持续集成 (CI)                                            │
│     • 代码拉取 (Pull Code)                                   │
│     • 依赖安装 (Install Dependencies)                        │
│     • 代码构建 (Build)                                       │
│     • 单元测试 (Unit Tests)                                  │
│     • 代码质量检查 (Lint/Code Quality)                       │
│     ↓                                                        │
│  🧪 持续测试                                                 │
│     • 集成测试 (Integration Tests)                           │
│     • 端到端测试 (E2E Tests)                                 │
│     • 安全扫描 (Security Scanning)                          │
│     ↓                                                        │
│  📦 持续交付/部署 (CD)                                       │
│     • 构建产物 (Build Artifacts)                             │
│     • 部署到测试环境 (Deploy to Staging)                     │
│     • [人工审核] (Manual Approval - 可选)                    │
│     • 部署到生产环境 (Deploy to Production)                  │
│     ↓                                                        │
│  ✅ 监控与反馈                                               │
│     • 应用监控 (Monitoring)                                  │
│     • 日志收集 (Logging)                                     │
│     • 告警通知 (Alerting)                                    │
└─────────────────────────────────────────────────────────────┘
```

### **关键概念**

**流水线（Pipeline）**
- 专业说：定义从代码到交付的一系列自动化步骤的配置文件
- 通俗说：CI/CD 的"生产流程图"，告诉系统每一步该做什么

**触发器（Trigger）**
- 专业说：启动 CI/CD 流水线的事件
- 通俗说：按下流水线"启动按钮"的动作
- 常见触发：代码推送、Pull Request、定时触发、手动触发

**构建产物（Artifacts）**
- 专业说：构建过程生成的可部署文件（如Docker镜像、JAR包、静态文件）
- 通俗说：流水线生产出的"产品"

**环境（Environment）**
- 专业说：应用运行的不同阶段（开发、测试、预发布、生产）
- 通俗说：产品的"质检车间"和"正式销售渠道"

## 📜 发展背景

### **起源与演进**

| 时间节点 | 里程碑事件 |
|---------|-----------|
| **2000年代初** | 敏捷开发兴起，频繁集成需求出现 |
| **2004年** | CruiseControl（最早的CI工具）诞生 |
| **2007-2008年** | DevOps运动开始，打破开发与运维的墙 |
| **2009年** | Jenkins 前身 Hudson 诞生，CI 开始普及 |
| **2010年代** | Docker/Kubernetes 出现，改变 CI/CD 方式 |
| **2015年** | GitOps 概念提出，Git 作为单一事实来源 |
| **2018年** | GitHub Actions 发布，CI/CD 与代码托管深度融合 |
| **2020年代** | 平台工程兴起，AI 驱动的 CI/CD 成为目标 |

### **演进趋势**

**从手动到自动**：手动部署 → 脚本化 → 流水线 → 智能化

**从单一到全面**：只关注构建 → CI → CI+CD → DevSecOps

**从服务器到云端**：自建服务器 → 云服务 → Serverless

**场景 1：前端项目自动化部署**

- **痛点**：每次更新都要手动构建、压缩、上传服务器，容易出错
- **方案**：使用 GitHub Actions 实现 CI/CD

**具体实现：**
```yaml
# .github/workflows/deploy.yml
name: Deploy to Production

on:
  push:
    branches: [main]

jobs:
  build-and-deploy:
    runs-on: ubuntu-latest
    
    steps:
      # 1. 检出代码
      - name: Checkout code
        uses: actions/checkout@v4
      
      # 2. 安装依赖
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      
      - name: Install dependencies
        run: npm ci
      
      # 3. 运行测试
      - name: Run tests
        run: npm test
      
      # 4. 构建项目
      - name: Build project
        run: npm run build
        env:
          VITE_API_URL: ${{ secrets.API_URL }}
      
      # 5. 部署到服务器
      - name: Deploy to server
        uses: easingthemes/ssh-deploy@main
        env:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          REMOTE_HOST: ${{ secrets.REMOTE_HOST }}
          REMOTE_USER: ${{ secrets.REMOTE_USER }}
          SOURCE: "dist/"
          TARGET: "/var/www/html"
```

- **效果**：推送代码后自动构建测试部署，全程无人工干预

**场景 2：后端 API 自动化测试与部署**

- **痛点**：测试覆盖不全，上线后才发现Bug
- **方案**：使用 GitLab CI 实现完整的测试部署流水线

**具体实现：**
```yaml
# .gitlab-ci.yml
stages:
  - build
  - test
  - deploy-staging
  - deploy-production

variables:
  DOCKER_IMAGE: $CI_REGISTRY_IMAGE:$CI_COMMIT_SHORT_SHA

# 构建阶段
build:
  stage: build
  image: docker:latest
  services:
    - docker:dind
  script:
    - docker login -u $CI_REGISTRY_USER -p $CI_REGISTRY_PASSWORD $CI_REGISTRY
    - docker build -t $DOCKER_IMAGE .
    - docker push $DOCKER_IMAGE

# 单元测试
unit-test:
  stage: test
  image: $DOCKER_IMAGE
  script:
    - npm run test:unit
  coverage: '/Lines\s*:\s*(\d+\.\d+)%/'

# 集成测试
integration-test:
  stage: test
  image: $DOCKER_IMAGE
  services:
    - postgres:15
    - redis:alpine
  variables:
    POSTGRES_DB: test_db
    POSTGRES_USER: test_user
    POSTGRES_PASSWORD: test_pass
  script:
    - npm run test:integration
    - npm run test:e2e

# 安全扫描
security-scan:
  stage: test
  image: securecodewarrior/docker-scan:latest
  script:
    - docker scan $DOCKER_IMAGE

# 部署到测试环境
deploy-staging:
  stage: deploy-staging
  image: bitnami/kubectl:latest
  script:
    - kubectl set image deployment/myapp myapp=$DOCKER_IMAGE -n staging
  environment:
    name: staging
    url: https://staging.example.com

# 部署到生产环境（需人工批准）
deploy-production:
  stage: deploy-production
  image: bitnami/kubectl:latest
  script:
    - kubectl set image deployment/myapp myapp=$DOCKER_IMAGE -n production
  environment:
    name: production
    url: https://example.com
  when: manual
  only:
    - main
```

- **效果**：代码推送后自动构建、测试、安全扫描，生产环境部署需要人工批准

**场景 3：微服务多项目协调部署**

- **痛点**：多个微服务需要按特定顺序部署，依赖关系复杂
- **方案**：使用 Jenkins 实现复杂的多项目流水线

**具体实现（Jenkinsfile）：**
```groovy
pipeline {
    agent any
    
    parameters {
        choice(name: 'ENVIRONMENT', choices: ['dev', 'staging', 'production'], description: '选择部署环境')
    }
    
    stages {
        // 并行构建所有服务
        stage('Parallel Build') {
            parallel {
                stage('Build Service A') {
                    steps {
                        dir('service-a') {
                            sh 'docker build -t myregistry/service-a:${BUILD_NUMBER} .'
                            sh 'docker push myregistry/service-a:${BUILD_NUMBER}'
                        }
                    }
                }
                stage('Build Service B') {
                    steps {
                        dir('service-b') {
                            sh 'docker build -t myregistry/service-b:${BUILD_NUMBER} .'
                            sh 'docker push myregistry/service-b:${BUILD_NUMBER}'
                        }
                    }
                }
                stage('Build Service C') {
                    steps {
                        dir('service-c') {
                            sh 'docker build -t myregistry/service-c:${BUILD_NUMBER} .'
                            sh 'docker push myregistry/service-c:${BUILD_NUMBER}'
                        }
                    }
                }
            }
        }
        
        // 按依赖顺序部署
        stage('Deploy Dependencies') {
            steps {
                script {
                    // 先部署基础服务
                    deploy('service-c', params.ENVIRONMENT)
                    deploy('service-b', params.ENVIRONMENT)
                }
            }
        }
        
        stage('Deploy Application') {
            steps {
                script {
                    // 最后部署主应用
                    deploy('service-a', params.ENVIRONMENT)
                }
            }
        }
        
        // 健康检查
        stage('Health Check') {
            steps {
                sh '''
                    #!/bin/bash
                    for service in service-a service-b service-c; do
                        kubectl rollout status deployment/$service -n ${ENVIRONMENT}
                    done
                '''
            }
        }
    }
    
    post {
        success {
            echo '🎉 部署成功！'
            // 通知团队
            slackSend(color: 'good', message: "部署成功: ${env.JOB_NAME} - ${env.BUILD_NUMBER}")
        }
        failure {
            echo '❌ 部署失败！'
            // 回滚
            sh 'kubectl rollback deployment/service-a -n ${ENVIRONMENT}'
            slackSend(color: 'danger', message: "部署失败: ${env.JOB_NAME} - ${env.BUILD_NUMBER}")
        }
    }
}

def deploy(service, env) {
    sh """
        kubectl set image deployment/${service} ${service}=myregistry/${service}:${BUILD_NUMBER} -n ${env}
        kubectl rollout status deployment/${service} -n ${env}
    """
}
```

- **效果**：并行构建、按序部署、自动健康检查、失败自动回滚

**场景 4：移动应用自动化发布**

- **痛点**：iOS 和 Android 打包签名繁琐，多渠道发布耗时
- **方案**：使用 GitHub Actions 实现多平台自动化发布

**具体实现：**
```yaml
# .github/workflows/release.yml
name: Release Mobile App

on:
  push:
    tags:
      - 'v*'

jobs:
  # iOS 构建
  build-ios:
    runs-on: macos-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
      
      - name: Install dependencies
        run: |
          cd mobile
          npm ci
      
      - name: Build iOS
        run: |
          cd mobile
          npx react-native build-ios --mode Release --scheme MyApp
        env:
          MATCH_PASSWORD: ${{ secrets.MATCH_PASSWORD }}
          FASTLANE_APPLE_APPLICATION_SPECIFIC_PASSWORD: ${{ secrets.APPLE_PASSWORD }}
      
      - name: Upload to TestFlight
        run: |
          cd mobile
          fastlane upload_to_testflight
        env:
          FASTLANE_USER: ${{ secrets.APPLE_ID }}
          FASTLANE_PASSWORD: ${{ secrets.APPLE_PASSWORD }}
          FASTLANE_APPLE_APPLICATION_SPECIFIC_PASSWORD: ${{ secrets.APPLE_PASSWORD }}

  # Android 构建
  build-android:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      
      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
      
      - name: Setup Java JDK
        uses: actions/setup-java@v4
        with:
          distribution: 'temurin'
          java-version: '17'
      
      - name: Install dependencies
        run: |
          cd mobile
          npm ci
      
      - name: Build Android
        run: |
          cd mobile/android
          ./gradlew assembleRelease
        env:
          KEYSTORE_PASSWORD: ${{ secrets.KEYSTORE_PASSWORD }}
          KEY_ALIAS: ${{ secrets.KEY_ALIAS }}
          KEY_PASSWORD: ${{ secrets.KEY_PASSWORD }}
      
      - name: Upload to Google Play
        uses: r0adkll/upload-google-play@v1
        with:
          serviceAccountJsonPlainText: ${{ secrets.GOOGLE_PLAY_SERVICE_ACCOUNT }}
          packageName: com.example.myapp
          releaseFiles: mobile/android/app/build/outputs/apk/release/app-release.apk
          track: internal

  # 多渠道打包
  build-android-channels:
    needs: build-android
    runs-on: ubuntu-latest
    strategy:
      matrix:
        channel: [xiaomi, huawei, oppo, vivo]
    steps:
      - uses: actions/checkout@v4
      
      - name: Build for ${{ matrix.channel }}
        run: |
          # 根据不同渠道打包
          ./build-channel.sh ${{ matrix.channel }}
      
      - name: Upload artifact
        uses: actions/upload-artifact@v4
        with:
          name: app-${{ matrix.channel }}.apk
          path: build/app-${{ matrix.channel }}.apk
```

- **效果**：打标签后自动构建 iOS/Android 版本并发布到各应用商店

## ⚖️ 优缺点分析

| 维度 | ✅ 优点 | ❌ 缺点/局限性 |
|------|---------|---------------|
| **效率** | 自动化提高交付速度，从数周到数分钟 | 初期搭建需要投入时间 |
| **质量** | 自动化测试确保代码质量 | 测试覆盖不全面仍有风险 |
| **安全性** | 可集成安全扫描，实现 DevSecOps | 配置不当可能泄露密钥 |
| **成本** | 开源工具免费，云服务按量付费 | 大规模使用云服务费用不低 |
| **维护** | 配置即代码，易于维护和迁移 | 工具链复杂，学习曲线陡 |
| **可靠性** | 标准化流程减少人为错误 | 流水线本身也可能出问题 |
