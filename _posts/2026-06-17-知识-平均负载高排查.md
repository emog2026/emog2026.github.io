# 📌 一句话总结
CPU、内存、IO任一环节出问题都会导致负载飙升

## 🎯 这是什么？

### 基础定义
**平均负载（Load Average）**：单位时间内，处于可运行状态（R）和不可中断睡眠状态（D）的进程平均数。

通俗讲：系统"忙碌程度"的指标，表示等待处理的任务队列长度。

### 通俗类比

**Load Average 就像收银台排队**：
```
超市有 4 个收银台（4 核 CPU）

Load = 1：平均 1 个人在排队，收银台很空闲
Load = 4：4 个收银台刚好都在忙，刚好饱和
Load = 8：平均 8 个人在排队，每个收银台有 2 个人等待，很拥挤

Load Average = 2, 4, 8：
- 最近 1 分钟平均 2 个人排队（正常）
- 最近 5 分钟平均 4 个人排队（饱和）
- 最近 15 分钟平均 8 个人排队（很忙，在恶化）
```

### 为什么存在
Load Average 是判断系统压力的核心指标：
- 快速判断系统是否过载
- 识别性能瓶颈（CPU/内存/IO）
- 预警潜在问题
- 指导扩容决策

## 🏗️ 核心原理

### Load Average 的三个数字

```bash
$ uptime
16:30:45 up 30 days,  2:15,  3 users,  load average: 2.50, 3.20, 4.80
                     │      │      │
                     1分钟  5分钟  15分钟
```

**解读规则**：
- **1分钟 < 5分钟 < 15分钟**：负载在下降，情况好转
- **1分钟 > 5分钟 > 15分钟**：负载在上升，需要关注
- **1分钟 >> 5分钟 ≈ 15分钟**：突发流量，可能瞬间过载

### 负载与 CPU 核数的关系

| CPU 核数 | 正常负载 | 需要关注 | 危险 |
|----------|----------|----------|------|
| 1 核 | < 1.0 | 1.0-2.0 | > 2.0 |
| 2 核 | < 2.0 | 2.0-4.0 | > 4.0 |
| 4 核 | < 4.0 | 4.0-8.0 | > 8.0 |
| 8 核 | < 8.0 | 8.0-16.0 | > 16.0 |

**计算公式**：
```bash
# 查看 CPU 核数
$ grep 'model name' /proc/cpuinfo | wc -l
4

# 判断负载健康度
Load / CPU 核数 = 比值
- 比值 < 1：健康
- 比值 1-2：需要关注
- 比值 > 2：严重过载

# 示例：4 核，Load = 8
比值 = 8 / 4 = 2（严重过载）
```

### 进程状态

```bash
$ top
  PID USER      PR  NI  VIRT  RES  %CPU %MEM    TIME+  S COMMAND
 1234 root      20   0  1024  256  98.0  0.1   1:23.45 R java  ← R：可运行（Running）
 5678 mysql     20   0  2048  512  45.2  0.2   5:67.89 D mysqld ← D：不可中断睡眠（Uninterruptible）
```

| 状态 | 说明 | 对负载的影响 |
|------|------|--------------|
| **R (Running)** | 可运行状态，等待 CPU | 直接贡献负载 |
| **D (Disk sleep)** | 不可中断睡眠，等待 IO | 直接贡献负载（重点关注） |
| **S (Sleeping)** | 可中断睡眠 | 不贡献负载 |

**关键理解**：
- **R 状态多**：CPU 繁忙（计算密集型）
- **D 状态多**：IO 繁忙（等待磁盘/网络）

## 📜 发展背景

- **Unix 时代**：Load Average 诞生于 BSD Unix（1970s）
- **Linux 继承**：Linux 从 Unix 继承此概念
- **现代演进**：
  - 支持多核 CPU
  - 细分 cgroup 负载
  - 容器化负载监控

## 💼 负载高的常见场景

### 场景 1：CPU 密集型任务 - 科学计算

**症状**：
```bash
$ uptime
load average: 8.50, 8.20, 7.90  # 4 核系统，Load = 8.5

$ top
%Cpu(s): 98.5 us,  0.0 sy,  0.0 ni,  1.5 id,  0.0 wa
        ━━━━━━━━━━━━━━━━━━━━━━ 98.5% 用户态 CPU
```

**原因分析**：
```bash
# 查看占用 CPU 的进程
$ top -o %CPU

  PID USER      %CPU  COMMAND
 1234 research  395  python  # 400% = 4 个核满载
 1235 research  392  python
 1236 research  388  python
 1237 research  385  python

# 查看进程详情
$ ps -fp 1234
UID        PID  PPID  C STIME TTY          TIME CMD
research 1234     1  99 10:00 ?        10:23:45 python data_analysis.py
```

**解决方案**：

**方案 1：调整进程优先级（临时）**
```bash
# 降低优先级，让其他进程优先运行
$ renice -n 19 -p 1234  # 最低优先级

# 或使用 ionice 调整 IO 优先级
$ ionice -c 3 -p 1234    # best-effort，最低优先级
```

**方案 2：限制 CPU 使用（推荐）**
```bash
# 使用 cpulimit 限制 CPU 使用
$ cpulimit -l 200 -p 1234  # 限制到 200% (2 核)

# 或使用 cgroups（现代方式）
$ cgcreate -g cpu:/research
$ echo 204800 > /sys/fs/cgroup/cpu/research/cpu.cfs_quota_us  # 限制 20% CPU
$ echo 1000000 > /sys/fs/cgroup/cpu/research/cpu.cfs_period_us
$ echo 1234 > /sys/fs/cgroup/cpu/research/tasks
```

**方案 3：优化代码（治本）**
```python
# 优化前：单进程循环
for i in range(10000000):
    heavy_calculation(i)

# 优化后：多进程并行
from multiprocessing import Pool
with Pool(processes=4) as pool:
    results = pool.map(heavy_calculation, range(10000000))

# 或使用 GPU 加速
import cupy as cp
result = cp.sum(cp.array(data))  # GPU 计算，释放 CPU
```

**方案 4：扩容或迁移**
```bash
# 迁移到专用服务器
# 1. 打包环境
$ tar czf research_env.tar.gz /opt/research

# 2. 传输到计算节点
$ scp research_env.tar.gz compute-node:/tmp/

# 3. 在计算节点运行（不影响生产服务器）
```

**效果**：
- Load 从 8.5 降到 2.0
- 其他服务恢复正常响应

### 场景 2：IO 密集型任务 - 数据库查询

**症状**：
```bash
$ uptime
load average: 12.0, 10.5, 9.0  # 4 核系统，Load = 12

$ top
%Cpu(s):  5.2 us, 10.3 sy,  0.0 ni, 20.5 id, 64.0 wa
        ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 64% IO 等待

$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- -----cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2 12      0 10240  2048 524288    0    0   120    10  120   50  5 10 20 65  0
              ━                          ━━━━━
              大量 D 状态                大量 IO 等待
```

**原因分析**：
```bash
# 查看谁在等待 IO
$ ps aux | awk '$8 ~ /D/'

USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
mysql     1234  0.5  5.0 123456 50000 ?        D    10:00   0:23 mysqld
mysql     1235  0.3  4.8 120000 48000 ?        D    10:00   0:21 mysqld
mysql     1236  0.4  5.1 124000 51000 ?        D    10:00   0:22 mysqld

# 查看进程在做什么
$ strace -p 1234
pread(3, ... 0x7fff, 4096) = 4096    # 正在读取磁盘
```

**解决方案**：

**方案 1：优化慢查询（治本）**
```sql
-- 查找慢查询
SELECT * FROM mysql.slow_log
ORDER BY query_time DESC
LIMIT 10;

-- 分析执行计划
EXPLAIN SELECT * FROM large_table WHERE status = 'pending';
-- 返回：type: ALL（全表扫描，需要优化）

-- 添加索引
CREATE INDEX idx_status ON large_table(status);

-- 验证
EXPLAIN SELECT * FROM large_table WHERE status = 'pending';
-- 返回：type: ref（使用索引，扫描行数从 100 万降到 100）
```

**方案 2：优化 IO 调度**
```bash
# 查看当前 IO 调度器
$ cat /sys/block/sda/queue/scheduler
noop [deadline] cfq

# 切换到 deadline（适合数据库）
$ echo deadline > /sys/block/sda/queue/scheduler

# 或使用 noop（SSD 推荐）
$ echo noop > /sys/block/sda/queue/scheduler
```

**方案 3：增加缓存**
```bash
# 增加 MySQL 缓冲池
# my.cnf
innodb_buffer_pool_size = 4G  # 从 1G 增加到 4G

# 重启 MySQL
$ systemctl restart mysql
```

**方案 4：升级到 SSD**
```bash
# 对比磁盘性能
$ hdparm -Tt /dev/sda
# HDD: ~100 MB/s

$ hdparm -Tt /dev/nvme0n1
# NVMe SSD: ~3000 MB/s（30 倍提升）

# 迁移数据到 SSD
$ rsync -av /var/lib/mysql/ /mnt/ssd/mysql/
$ mount /dev/nvme0n1 /var/lib/mysql
```

**效果**：
- Load 从 12 降到 3
- IO 等待从 64% 降到 10%
- 查询速度提升 5-10 倍

### 场景 3：内存不足 - Swap 换页

**症状**：
```bash
$ uptime
load average: 6.0, 5.5, 5.0

$ free -h
              total        used        free      shared  buff/cache   available
Mem:           7.6G        7.2G        100M        50M        300M        100M
Swap:          4.0G        3.8G        200M
               ━━━━━━━━━━━━━━━━━━━━━━━━
               内存几乎用完，大量 Swap

$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- -----cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 3  2  4000  10000  2048  3000  500  450  1000   900  150  100 10 20 20 50  0
            ━━━━━━━━━━━━━━━━━━━━━━
            大量 Swap 换入换出（si/so 高）
```

**原因分析**：
```bash
# 查看内存使用 Top 10
$ ps aux --sort=-%mem | head -n 11

USER       PID %MEM    VSZ   RSS COMMAND
app       1234 45.2 1234567 3456780 java   # Java 应用占用 4.5GB
app       1235 38.5 1123456 2928000 java
app       1236 25.1  987654 1907604 java

# 查看 JVM 配置
$ ps -p 1234 -o args
java -Xms4g -Xmx4g ...  # 堆内存 4GB
```

**解决方案**：

**方案 1：优化应用内存使用（治本）**
```java
// 优化前：一次性加载所有数据到内存
List<Order> orders = orderRepository.findAll(); // 100 万订单
processOrders(orders);

// 优化后：分批处理
int pageSize = 1000;
int page = 0;
List<Order> orders;
do {
    orders = orderRepository.findAll(PageRequest.of(page++, pageSize));
    processOrders(orders);
} while (!orders.isEmpty());
```

**方案 2：调整 Swap 策略（临时）**
```bash
# 查看 Swap 优先级
$ cat /proc/sys/vm/swappiness
60

# 降低 Swap 使用（尽可能用物理内存）
$ sysctl vm.swappiness=10
$ echo "vm.swappiness=10" >> /etc/sysctl.conf

# 禁用 Swap（如果有足够内存）
$ swapoff -a
```

**方案 3：增加内存（推荐）**
```bash
# 查看内存插槽数
$ dmidecode -t memory | grep -i size

# 增加内存条（如果主板有插槽）
# 或升级到内存更大的服务器
```

**方案 4：容器化限制内存**
```yaml
# docker-compose.yml
services:
  app:
    image: myapp:latest
    deploy:
      resources:
        limits:
          memory: 2G  # 限制内存 2GB
```

**效果**：
- Swap 使用从 3.8GB 降到接近 0
- Load 从 6 降到 1.5
- 系统响应恢复正常

### 场景 4：网络流量突增 - DDoS 攻击

**症状**：
```bash
$ uptime
load average: 15.0, 12.0, 8.0

$ netstat -an | wc -l
15234  # 大量连接

$ netstat -an | grep TIME_WAIT | wc -l
12000  # 大量 TIME_WAIT 状态

$ top
%Cpu(s): 10.0 us, 40.0 sy,  0.0 ni, 10.0 id, 40.0 wa
        ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━ 40% 系统态，网络处理
```

**原因分析**：
```bash
# 查看连接来源
$ netstat -an | grep ESTABLISHED | awk '{print $5}' | cut -d: -f1 | sort | uniq -c | sort -rn | head -10

   500 192.168.1.100
   450 192.168.1.101
   300 10.0.0.50
   ...
   ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   单个 IP 大量连接

# 检查是否被攻击
$ tcpdump -i eth0 -n -c 100 'tcp[tcpflags] & (tcp-syn) != 0'
```

**解决方案**：

**方案 1：使用防火墙封禁 IP**
```bash
# 使用 iptables 限制单 IP 连接数
$ iptables -A INPUT -p tcp --dport 80 -m connlimit \
  --connlimit-above 50 -j REJECT

# 封禁恶意 IP
$ iptables -A INPUT -s 192.168.1.100 -j DROP

# 保存规则
$ iptables-save > /etc/iptables/rules.v4
```

**方案 2：优化内核网络参数**
```bash
# /etc/sysctl.conf
net.ipv4.tcp_syncookies = 1          # 启用 SYN Cookies
net.ipv4.tcp_max_syn_backlog = 4096  # 增加 SYN 队列
net.ipv4.tcp_synack_retries = 2      # 减少 SYN-ACK 重试
net.ipv4.tcp_fin_timeout = 30        # 减少 FIN 超时
net.core.somaxconn = 65535           # 增加连接队列

# 应用配置
$ sysctl -p
```

**方案 3：使用 CDN/WAF**
```nginx
# Nginx 配置限流
http {
    limit_req_zone $binary_remote_addr zone=one:10m rate=10r/s;

    server {
        location / {
            limit_req zone=one burst=20 nodelay;
            # 每秒最多 10 个请求，突发 20 个
        }
    }
}
```

**方案 4：使用云服务 DDoS 防护**
```bash
# 启用云厂商的 DDoS 防护
# AWS: Shield、CloudFront
# 阿里云: Anti-DDoS Pro
# Cloudflare: 免费基础防护
```

**效果**：
- 恶意连接被阻断
- Load 从 15 降到 3
- 正常用户可正常访问

### 场景 5：僵尸进程/孤儿进程累积

**症状**：
```bash
$ uptime
load average: 5.0, 4.5, 4.0

$ ps aux | grep defunct | wc -l
1500  # 大量僵尸进程

$ ps aux | grep Z | head -5
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
app       1234  0.0  0.0      0     0 ?        Z    10:00   0:00 [python] <defunct>
app       1235  0.0  0.0      0     0 ?        Z    10:00   0:00 [python] <defunct>
```

**原因分析**：
```bash
# 查看僵尸进程的父进程
$ ps -o pid,ppid,stat,command -p 1234

  PID  PPID STAT COMMAND
 1234  1000 Z   [python] <defunct>

# 查看父进程是谁
$ ps -p 1000
  PID USER      %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
 1000 app       15.0  2.0 123456 20000 ?        Ss   10:00   5:23 gunicorn
                    ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
                    父进程没有回收子进程
```

**解决方案**：

**方案 1：修复应用代码（治本）**
```python
# 问题代码
while True:
    process = subprocess.Popen(['sleep', '10'])
    # 没有等待进程结束，导致僵尸进程

# 修复代码
while True:
    process = subprocess.Popen(['sleep', '10'])
    process.wait()  # 等待进程结束，回收资源
```

**方案 2：重启父进程**
```bash
# 找到父进程 PID
$ ps -o pid,ppid,stat,command -p 1234 | grep defunct

# 重启父进程
$ kill -HUP 1000  # 尝试优雅重启
# 或
$ systemctl restart app-service  # 通过服务重启
```

**方案 3：清理僵尸进程（临时）**
```bash
# 僵尸进程无法直接 kill，需要 kill 父进程
$ kill -9 1000  # 父进程被杀，僵尸进程被 init 接管并清理

# 或使用专门的脚本
$ kill -9 $(ps -A -o stat=,pid= | grep -e 'Z.*' | awk '{print $2}')
```

**效果**：
- 僵尸进程被清理
- Load 从 5 降到 1
- 系统恢复正常

## 🔮 最佳实践

### 1. 建立监控告警

```bash
# 使用 cron 定期检查
*/5 * * * * /usr/local/bin/check-load.sh

#!/bin/bash
# check-load.sh
LOAD=$(uptime | awk '{print $10}' | cut -d, -f1)
THRESHOLD=4.0

if (( $(echo "$LOAD > $THRESHOLD" | bc -l) )); then
    echo "Load Average: $LOAD" | mail -s "High Load Alert" admin@example.com
fi
```

```yaml
# Prometheus 配置
groups:
  - name: node_alerts
    rules:
      - alert: HighLoadAverage
        expr: node_load1 > node_num_cpu * 2
        for: 5m
        annotations:
          summary: "Load Average high on {{ $labels.instance }}"
```
