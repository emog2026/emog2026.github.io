> 📚 知识关键词：MySQL主从复制

---

# 📌 一句话总结
主库负责写数据，从库自动同步，实现读写分离、高可用和数据备份

## 🎯 这是什么？

### 基础定义
MySQL 主从复制是一种数据库复制技术，将一台 MySQL 服务器（主库/Master）的数据变更自动同步到一台或多台其他 MySQL 服务器（从库/Slave）。

### 通俗类比
想象一个公司有两个公告栏：
- **主公告栏**：行政人员张贴新通知（写操作）
- **从公告栏**：自动同步主公告栏的内容，员工只能看（读操作）

这样：
- 行政人员只需要在一个地方张贴（写在一个库）
- 员工可以分散在多个公告栏前查看（分散读取压力）
- 如果主公告栏坏了，从公告栏还有完整备份（数据安全）

### 为什么存在
解决四个核心问题：
1. **性能瓶颈**：单库扛不住高并发读写
2. **数据安全**：需要实时备份防止数据丢失
3. **地理分布**：用户在不同地区，需要就近访问
4. **灾难恢复**：主库故障时能快速切换

## 🏗️ 核心原理

### 它是如何工作的

```
┌─────────────┐     ① binlog      ┌──────────────┐
│   Master    │ ────────────────> │  Slave I/O   │
│  (主库)     │                    │    Thread    │
│             │ <────────────────  │              │
└─────────────┘     ④ 确认        └──────────────┘
      │                            │
      │ ③ 写入 relay log           │
      ▼                            ▼
┌─────────────┐              ┌──────────────┐
│   binlog    │              │  relay log   │
│  (二进制日志)│              │  (中继日志)   │
└─────────────┘              └──────────────┘
                                         │
                                         │ ⑤ 重放
                                         ▼
                                  ┌──────────────┐
                                  │ Slave SQL    │
                                  │   Thread     │
                                  └──────────────┘
```

### 工作流程

**步骤 1：主库记录变更**
- 主库执行 INSERT/UPDATE/DELETE
- 变更记录到 binlog（二进制日志）

**步骤 2：从库 IO 线程拉取**
- 从库 IO 线程连接主库
- 请求 binlog 并写入 relay log（中继日志）

**步骤 3：从库 SQL 线程执行**
- 从库 SQL 线程读取 relay log
- 重放 SQL 语句，实现数据同步

### 关键概念

**binlog（二进制日志）**
- 专业说：记录所有数据变更操作的日志文件
- 通俗说：主库的"日记本"，记下所有改动

**relay log（中继日志）**
- 专业说：从库保存从主库接收的 binlog 事件
- 通俗说：从库的"抄写本"，抄完再执行

**IO 线程**
- 专业说：负责从主库拉取 binlog 并写入 relay log
- 通俗说：搬运工，把主库的日记抄过来

**SQL 线程**
- 专业说：负责读取 relay log 并重放 SQL
- 通俗说：执行者，按抄写本执行命令

**GTID（全局事务 ID）**
- 专业说：全局唯一的事务标识符
- 通俗说：给每个事务发"身份证"，追踪更容易

**复制模式**

| 模式 | 说明 | 优缺点 |
|------|------|--------|
| 异步复制 | 主库不等待从库确认 | 性能好，可能丢数据 |
| 半同步复制 | 主库等待至少一个从库确认 | 平衡性能和安全 |
| 全同步复制 | 所有从库都确认才返回 | 最安全，性能差 |

## 📜 发展背景

- **起源**：MySQL 3.23.15（2000年）引入基本主从复制
- **演进**：
  - 2005：MySQL 5.0 引入基于语句的复制
  - 2010：MySQL 5.5 引入半同步复制
  - 2013：MySQL 5.6 引入 GTID
  - 2015：MySQL 5.7 多线程复制，支持并行复制
  - 2018：MySQL 8.0 优化复制性能
- **当前状态**：成熟技术，广泛用于生产环境

## 💼 应用场景

### 场景 1：读写分离 - 电商系统

**痛点**：
- 双十一大促，读流量是写流量的 10 倍
- 单库扛不住，响应变慢

**方案**：
主库负责写订单，3 台从库负责读商品信息

**具体实现**：

```ini
# 主库 my.cnf
[mysqld]
server-id = 1
log-bin = mysql-bin
binlog-format = ROW
```

```sql
-- 主库创建复制用户
CREATE USER 'repl_user'@'%' IDENTIFIED BY 'StrongPassword123!';
GRANT REPLICATION SLAVE ON *.* TO 'repl_user'@'%';
FLUSH PRIVILEGES;

-- 记录 binlog 位置
SHOW MASTER STATUS;
-- 输出示例：
-- File: mysql-bin.000003
-- Position: 154
```

```bash
# 主库备份
mysqldump -u root -p --all-databases --master-data=2 > master_backup.sql
```

```ini
# 从库 my.cnf
[mysqld]
server-id = 2  # 每台从库不同
relay-log = relay-bin
read-only = 1
```

```bash
# 从库导入备份
mysql -u root -p < master_backup.sql
```

```sql
-- 从库配置主库信息
CHANGE MASTER TO
  MASTER_HOST='192.168.1.100',
  MASTER_USER='repl_user',
  MASTER_PASSWORD='StrongPassword123!',
  MASTER_LOG_FILE='mysql-bin.000003',
  MASTER_LOG_POS=154;

START SLAVE;

-- 验证状态
SHOW SLAVE STATUS\G
-- 检查：Slave_IO_Running: Yes, Slave_SQL_Running: Yes
```

**效果**：
- 读流量分散到 3 台从库
- 主库专注写入，延迟降低 70%

### 场景 2：数据备份与容灾 - 金融系统

**痛点**：
- 金融数据不能丢
- 机房断电需要快速恢复

**方案**：
本地主库 + 远程从库（异地容灾）

**具体实现**：

```ini
# 主库开启半同步复制
[mysqld]
plugin-load = "rpl_semi_sync_master=semisync_master.so"
rpl_semi_sync_master_enabled = 1
rpl_semi_sync_master_timeout = 1000
```

```ini
# 从库（异地）配置
[mysqld]
server-id = 10
plugin-load = "rpl_semi_sync_slave=semisync_slave.so"
rpl_semi_sync_slave_enabled = 1
```

```sql
-- 从库配置
CHANGE MASTER TO
  MASTER_HOST='主库公网IP',
  MASTER_USER='repl_user',
  MASTER_PASSWORD='StrongPassword123!',
  MASTER_AUTO_POSITION = 1;  -- 使用 GTID

START SLAVE;
```

```bash
# 定期验证从库数据
# 从库上执行
mysql -u root -p -e "SHOW SLAVE STATUS\G" | grep Seconds_Behind_Master
```

**效果**：
- RPO（数据丢失时间）< 1秒
- 异地机房可快速切换

### 场景 3：报表分析 - SaaS 平台

**痛点**：
- 生成报表要扫描全表
- 分析查询拖慢主业务

**方案**：
专门从库跑报表，不影响主库

**具体实现**：

```ini
# 报表从库配置
[mysqld]
server-id = 3
read-only = 1
# 允许长时间运行的报表查询
max_execution_time = 0
```

```sql
-- 在报表从库执行分析
-- 不会影响主库性能
SELECT
    DATE(created_at) as date,
    COUNT(*) as new_users,
    SUM(payment_amount) as revenue
FROM users
WHERE created_at >= DATE_SUB(NOW(), INTERVAL 30 DAY)
GROUP BY DATE(created_at);
```

**效果**：
- 报表查询不影响主业务
- 可随时运行复杂分析

### 场景 4：GTID 自动故障转移

**痛点**：
- 传统基于 binlog 位置的复制，切换复杂
- 主库故障，从库提升麻烦

**方案**：
使用 GTID + MHA 自动化故障转移

**具体实现**：

```ini
# 所有服务器开启 GTID
[mysqld]
gtid_mode = ON
enforce_gtid_consistency = ON
log-bin = mysql-bin
binlog-format = ROW
log_slave_updates = ON  # 从库也记录 binlog，支持级联复制
```

```sql
-- 从库配置（简化，无需指定 binlog 位置）
CHANGE MASTER TO
  MASTER_HOST='192.168.1.100',
  MASTER_USER='repl_user',
  MASTER_PASSWORD='StrongPassword123!',
  MASTER_AUTO_POSITION = 1;

START SLAVE;
```

```bash
# 安装 MHA Manager
# 在管理服务器上
wget https://github.com/yoshinorim/mha4mysql-manager/releases/tag/v0.58
perl Makefile.PL
make && make install

# 配置 MHA
cat > /etc/mha/app1.cnf <<EOF
[server1]
hostname=192.168.1.100
candidate_master=1

[server2]
hostname=192.168.1.101
candidate_master=1

[server3]
hostname=192.168.1.102
no_master=1
EOF

# 启动 MHA 监控
nohup masterha_manager --conf=/etc/mha/app1.cnf > /var/log/mha.log 2>&1 &
```

**效果**：
- 主库故障 30 秒内自动切换
- GTID 确保数据一致性

## ⚖️ 优缺点分析

| 维度 | ✅ 优点 | ❌ 缺点/局限性 |
|------|---------|---------------|
| 性能 | 读写分离，提升吞吐 | 从库有延迟，可能读到旧数据 |
| 可用性 | 主库故障可快速切换 | 需要额外工具实现自动切换 |
| 扩展性 | 可无限添加从库 | 写入无法扩展，仍是单点 |
| 数据安全 | 实时备份，异步/半同步 | 异步模式可能丢数据 |
| 运维成本 | 技术成熟，社区支持好 | 需要监控、维护、故障排查 |

## 🔍 常见问题排查

### 主从延迟监控

```sql
-- 从库执行
SHOW SLAVE STATUS\G

-- 关键字段
-- Slave_IO_Running: Yes    -- IO 线程状态
-- Slave_SQL_Running: Yes   -- SQL 线程状态
-- Seconds_Behind_Master: 0 -- 延迟秒数（0 表示无延迟）
```

### 常见错误处理

**错误 1062：重复键**
```sql
-- 跳过错误（慎用）
STOP SLAVE;
SET GLOBAL sql_slave_skip_counter = 1;
START SLAVE;
```

**复制中断恢复**
```sql
-- 使用 GTID 跳过特定事务
STOP SLAVE;
SET GTID_NEXT='冲突的 GTID';
BEGIN; COMMIT;
SET GTID_NEXT='AUTOMATIC';
START SLAVE;
```

### 性能优化

```ini
# 从库启用并行复制（MySQL 5.7+）
[mysqld]
slave_parallel_type = LOGICAL_CLOCK
slave_parallel_workers = 4  # 根据CPU核心数调整
```
