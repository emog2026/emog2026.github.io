> 📚 知识关键词：Kubernetes、健康检查、优雅停止、动态伸缩

📌 **一句话总结**：Kubernetes 的"三大利器"，确保应用健康运行、平稳更新、弹性伸缩，实现零宕机的自动化运维

---

## 🎯 这是什么？

### **基础定义**
这三个是 Kubernetes 的核心运维机制，共同保障应用的高可用性：

**健康检查（Health Check）**
- 通过探针（Probe）检测容器健康状态
- 三种类型：存活探针、就绪探针、启动探针
- 自动恢复异常应用

**优雅停止（Graceful Shutdown）**
- Pod 删除时给应用时间完成清理工作
- 通过 PreStop Hook 和 terminationGracePeriodSeconds 控制
- 确保请求完成、连接关闭、资源释放

**动态伸缩（Autoscaling）**
- 根据负载自动调整 Pod 数量
- 水平伸缩：调整 Pod 副本数
- 垂直伸缩：调整 Pod 资源配额

### **通俗类比**
把 Kubernetes 想象成一个"智能工厂管理系统"：
- **健康检查**像"质检员"——持续检查设备是否正常运行，发现故障自动重启
- **优雅停止**像"下班流程"——关机前保存工作、清理现场、通知相关方
- **动态伸缩**像"弹性调度"——订单多时加派人手，订单少时减少人手

### **为什么存在**
解决容器化运维的三大痛点：
1. **应用故障**：容器崩溃或死锁无法自动恢复
2. **部署中断**：更新时服务中断影响用户
3. **资源浪费**：负载低时资源浪费，负载高时性能不足

## 🏗️ 核心原理

### **一、健康检查是如何工作的**

Kubernetes 通过三种探针实现健康检查：

```
┌─────────────────────────────────────────────────────────────┐
│                Kubernetes 三种探针机制                         │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  💓 存活探针 (Liveness Probe)                               │
│     目的：检测容器是否需要重启                                │
│     失败行为：重启容器                                       │
│     配置参数：periodSeconds、failureThreshold、timeoutSeconds│
│     适用场景：应用死锁、内存泄漏等无法自动恢复的故障          │
│                                                              │
│  ✅ 就绪探针 (Readiness Probe)                               │
│     目的：检测容器是否准备好接收流量                          │
│     失败行为：从 Service 中移除，不重启容器                   │
│     配置参数：periodSeconds、failureThreshold、successThreshold│
│     适用场景：应用启动依赖其他服务、加载缓存                  │
│                                                              │
│  🚀 启动探针 (Startup Probe)                                │
│     目的：检测慢启动应用是否启动成功                          │
│     失败行为：重启容器                                       │
│     配置参数：periodSeconds、failureThreshold                 │
│     适用场景：需要几分钟才能启动的应用                        │
│     特殊机制：成功后就禁用，由 Liveness/Readiness 接管      │
└─────────────────────────────────────────────────────────────┘
```

**探针检测方式对比**：

| 方式 | 适用场景 | 优点 | 缺点 |
|------|---------|------|------|
| **HTTP** | Web 应用、API 服务 | 简单、标准化 | 需要暴露 HTTP 端口 |
| **TCP** | 数据库、缓存服务 | 快速、简单 | 只能检测端口连通性 |
| **Exec**（执行命令） | 任何类型应用 | 灵活、可自定义 | 复杂，可能超时 |

**探针时间线关系**：
```
容器启动
  ↓
[Startup Probe] ← 失败则重启
  ↓ 成功后禁用
[Liveness Probe] ← 持续运行，失败则重启
[Readiness Probe] ← 持续运行，失败则移出Service
```

### **二、优雅停止是如何工作的**

Pod 终止流程详解：

```
┌─────────────────────────────────────────────────────────────┐
│                  Pod 终止生命周期                             │
├─────────────────────────────────────────────────────────────┤
│  1️⃣ 用户或控制器删除 Pod                                    │
│     • kubectl delete                                        │
│     • Deployment 更新触发滚动更新                             │
│                                                              │
│  2️⃣ Pod 状态变为 Terminating                                │
│     • endpoint controller 从 Service 移除 Pod IP              │
│     • 不再接收新流量                                         │
│                                                              │
│  3️⃣ 执行 PreStop Hook                                      │
│     • lifecycle.preStop 配置的脚本                          │
│     • 最多执行 terminationGracePeriodSeconds 的时间          │
│                                                              │
│  4️⃣ 容器进程收到 SIGTERM 信号                               │
│     • 应用开始优雅停止                                       │
│     • 完成正在进行中的请求                                   │
│     • 关闭数据库连接、释放资源                               │
│                                                              │
│  5️⃣ 等待容器进程结束                                        │
│     • 默认 30 秒宽限期                                       │
│     • 超时后发送 SIGKILL 强制终止                            │
│                                                              │
│  6️⃣ Pod 完全删除                                            │
└─────────────────────────────────────────────────────────────┘
```

**关键配置**：
- **terminationGracePeriodSeconds**：宽限期（默认 30 秒）
- **lifecycle.preStop**：停止前执行的钩子
- **SIGTERM 信号处理**：应用需要正确处理信号

### **三、动态伸缩是如何工作的**

#### **水平伸缩**

```
┌─────────────────────────────────────────────────────────────┐
│             HPA (Horizontal Pod Autoscaler) 工作流程         │
├─────────────────────────────────────────────────────────────┤
│  📊 Metrics Server 持续采集指标                              │
│     • CPU 使用率                                             │
│     • 内存使用率                                             │
│     • 自定义指标（QPS、延迟等）                              │
│                                                              │
│  🔄 HPA Controller 周期性检查（默认 15 秒）                  │
│     • 计算当前副本数是否满足目标值                           │
│     • 根据公式计算期望副本数                                 │
│     • 期望副本数 = ceil(当前指标值 / 目标指标值 × 当前副本数) │
│                                                              │
│  ⚖️ 调整副本数                                              │
│     • 调用 Scale 子资源调整 Deployment 副本数                │
│     • 遵循 maxReplicas 和 minReplicas 限制                   │
│     • 滚动更新确保零宕机                                     │
└─────────────────────────────────────────────────────────────┘
```

**HPA 关键参数**：
```yaml
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2                  # 最小副本数
  maxReplicas: 10                 # 最大副本数
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization       # 使用率类型
          averageUtilization: 50   # 目标 CPU 使用率 50%
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 60    # 稳定窗口
      policies:
        - type: Pods
          value: 4                         # 最多增加 4 个 Pod
          periodSeconds: 15                # 每 15 秒检查一次
    scaleDown:
      stabilizationWindowSeconds: 300   # 缩容稳定窗口 5 分钟
      policies:
        - type: Pods
          value: 2                         # 最多减少 2 个 Pod
          periodSeconds: 60                # 每 60 秒检查一次
```

#### **垂直伸缩**

VPA (Vertical Pod Autoscaler) 工作流程：
- **监控**：持续监控 Pod 的资源使用情况
- **推荐**：基于历史数据推荐最佳的 CPU/内存 Request 和 Limit
- **更新**：自动更新 Pod 的资源配额（需要重启 Pod）

**三种模式**：
- **Off**：只推荐，不自动应用
- **Initial**：仅在 Pod 创建时应用推荐值
- **Recreate**：自动应用推荐值，需要重建 Pod

**注意**：HPA 和 VPA 不能同时使用相同的资源指标（CPU/内存）。

## 📜 发展背景

### **起源与演进**

| 时间节点 | 里程碑事件 |
|---------|-----------|
| **2014年** | Kubernetes v1.0 发布，基础探针支持 |
| **2016年** | HPA (Horizontal Pod Autoscaler) 引入 |
| **2018年** | VPA (Vertical Pod Autoscaler) 作为 beta 功能引入 |
| **2019年** | Startup Probe 引入，解决慢启动应用问题 |
| **2020年** | HPA 支持自定义指标 |
| **2021年** | VPA 正式发布 (GA) |
| **2022年** | HPA 行为策略（Behavior Policy）引入 |
| **2023年** | 基于机器学习的智能伸缩探索 |

### **演进特点**

**从手动到自动**：手动调整副本 → 基于阈值的自动伸缩 → 智能预测伸缩

**从单一到多元**：CPU/内存指标 → 自定义指标 → 多指标组合

**从粗糙到精细**：简单比例伸缩 → 行为策略控制 → 个性化伸缩策略

**场景 1：Web 应用健康检查配置**

- **痛点**：应用异常时无法自动恢复，用户遇到 502 错误
- **方案**：配置 Liveness 和 Readiness 探针

**具体实现：**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: webapp
  template:
    metadata:
      labels:
        app: webapp
    spec:
      containers:
        - name: webapp
          image: myapp:1.0
          ports:
            - containerPort: 8080
          
          # 存活探针：检测应用是否存活
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 30      # 容器启动后等待 30 秒
            periodSeconds: 10             # 每 10 秒检查一次
            timeoutSeconds: 5              # 超时时间 5 秒
            failureThreshold: 3            # 连续 3 次失败后重启
            successThreshold: 1            # 成功 1 次即认为健康
          
          # 就绪探针：检测应用是否准备好接收流量
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 10      # 容器启动后等待 10 秒
            periodSeconds: 5              # 每 5 秒检查一次
            timeoutSeconds: 3              # 超时时间 3 秒
            failureThreshold: 3            # 连续 3 次失败后标记为未就绪
            successThreshold: 1            # 成功 1 次即认为就绪
          
          # 资源配额
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
```

**/health/live 端点示例**（Go）：
```go
package main

import (
    "net/http"
)

func livenessHandler(w http.ResponseWriter, r *http.Request) {
    // 简单的存活检查：能响应就说明活着
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("OK"))
}

func readinessHandler(w http.ResponseWriter, r *http.Request) {
    // 就绪检查：检查依赖服务是否可用
    if !isDatabaseReady() {
        w.WriteHeader(http.StatusServiceUnavailable)
        w.Write([]byte("Database not ready"))
        return
    }
    if !isCacheReady() {
        w.WriteHeader(http.StatusServiceUnavailable)
        w.Write([]byte("Cache not ready"))
        return
    }
    w.WriteHeader(http.StatusOK)
    w.Write([]byte("Ready"))
}
```

- **效果**：应用异常时自动重启，依赖未就绪时从 Service 中移除

**场景 2：慢启动应用的优雅停止**

- **痛点**：应用启动需要几分钟，更新时正在处理的请求中断
- **方案**：配置 Startup Probe 和 PreStop Hook

**具体实现：**
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: slowapp
spec:
  replicas: 3
  selector:
    matchLabels:
      app: slowapp
  template:
    metadata:
      labels:
        app: slowapp
    spec:
      containers:
        - name: slowapp
          image: slowapp:1.0
          ports:
            - containerPort: 8080
          
          # 启动探针：给慢启动应用足够时间
          startupProbe:
            httpGet:
              path: /health/startup
              port: 8080
            initialDelaySeconds: 0       # 立即开始检查
            periodSeconds: 10             # 每 10 秒检查一次
            timeoutSeconds: 5              # 超时时间 5 秒
            failureThreshold: 30           # 最多允许 30 次失败（5分钟）
            successThreshold: 1            # 成功 1 次即可
          
          # 存活探针
          livenessProbe:
            httpGet:
              path: /health/live
              port: 8080
            initialDelaySeconds: 30
            periodSeconds: 10
            failureThreshold: 3
          
          # 就绪探针
          readinessProbe:
            httpGet:
              path: /health/ready
              port: 8080
            initialDelaySeconds: 10
            periodSeconds: 5
            failureThreshold: 3
          
          # 优雅停止配置
          lifecycle:
            preStop:
              exec:
                command:
                  - /bin/sh
                  - -c
                  - |
                    # 1. 标记为不可服务
                    curl -X POST http://localhost:8080/health/disable
                    
                    # 2. 等待一段时间让负载均衡器更新
                    sleep 10
                    
                    # 3. 优雅关闭：处理完剩余请求
                    curl -X POST http://localhost:8080/shutdown
                    
                    # 等待实际关闭完成
                    sleep 5
          
          # 终止宽限期（默认 30 秒，可根据需要调整）
          # terminationGracePeriodSeconds: 60
```

**应用端优雅停止实现**（Go）：
```go
package main

import (
    "context"
    "log"
    "net/http"
    "os"
    "os/signal"
    "syscall"
    "time"
)

var (
    server    *http.Server
    healthy   = true
    shuttingDown = false
)

func main() {
    server = &http.Server{
        Addr: ":8080",
    }

    http.HandleFunc("/health/live", livenessHandler)
    http.HandleFunc("/health/ready", readinessHandler)
    http.HandleFunc("/health/disable", func(w http.ResponseWriter, r *http.Request) {
        healthy = false
        w.WriteHeader(http.StatusOK)
    })
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        if !healthy {
            http.Error(w, "Shutting down", http.StatusServiceUnavailable)
            return
        }
        time.Sleep(100 * time.Millisecond) // 模拟处理时间
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("Hello"))
    })
    http.HandleFunc("/shutdown", func(w http.ResponseWriter, r *http.Request) {
        shuttingDown = true
        w.WriteHeader(http.StatusOK)
    })

    // 启动服务器
    go func() {
        log.Println("Server starting")
        if err := server.ListenAndServe(); err != nil && err != http.ErrServerClosed {
            log.Fatalf("Server error: %v", err)
        }
    }()

    // 等待信号
    sigChan := make(chan os.Signal, 1)
    signal.Notify(sigChan, syscall.SIGINT, syscall.SIGTERM)
    <-sigChan

    log.Println("Shutting down gracefully...")
    
    // 创建超时上下文
    ctx, cancel := context.WithTimeout(context.Background(), 25*time.Second)
    defer cancel()

    // 优雅关闭
    if err := server.Shutdown(ctx); err != nil {
        log.Printf("Shutdown error: %v", err)
    }
    log.Println("Server stopped")
}

func livenessHandler(w http.ResponseWriter, r *http.Request) {
    if !shuttingDown {
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("OK"))
    } else {
        w.WriteHeader(http.StatusServiceUnavailable)
    }
}

func readinessHandler(w http.ResponseWriter, r *http.Request) {
    if healthy && !shuttingDown {
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("Ready"))
    } else {
        w.WriteHeader(http.StatusServiceUnavailable)
    }
}
```

- **效果**：慢启动应用不会因超时被重启，停止时处理完剩余请求

**场景 3：基于 CPU 使用率的水平伸缩**

- **痛点**：高峰期响应慢，低峰期资源浪费
- **方案**：配置 HPA 自动调整副本数

**具体实现：**
```yaml
# 1. 先部署应用
apiVersion: apps/v1
kind: Deployment
metadata:
  name: myapp
spec:
  replicas: 2
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      labels:
        app: myapp
    spec:
      containers:
        - name: myapp
          image: myapp:1.0
          ports:
            - containerPort: 8080
          resources:
            requests:
              cpu: 100m        # 必须设置 requests
              memory: 128Mi
            limits:
              cpu: 500m
              memory: 512Mi
---
# 2. 部署 HPA
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2              # 最小副本数
  maxReplicas: 10             # 最大副本数
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50  # 目标 CPU 使用率 50%
  behavior:
    scaleUp:
      stabilizationWindowSeconds: 0    # 快速扩容
      policies:
        - type: Pods
          value: 4                         # 每次最多增加 4 个
          periodSeconds: 15                # 每 15 秒
        - type: Percent
          value: 100                       # 或每次增加 100%
          periodSeconds: 15
    scaleDown:
      stabilizationWindowSeconds: 300   # 缩容稳定窗口 5 分钟
      policies:
        - type: Pods
          value: 1                         # 每次最多减少 1 个
          periodSeconds: 60                # 每 60 秒
```

**部署和测试**：
```bash
# 1. 确保集群安装了 Metrics Server
kubectl get deployment metrics-server -n kube-system

# 如果没有，安装：
kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

# 2. 部署应用和 HPA
kubectl apply -f myapp-deployment.yaml
kubectl apply -f myapp-hpa.yaml

# 3. 查看 HPA 状态
kubectl get hpa

# 4. 产生负载测试
kubectl run -i --tty load-generator --image=busybox /bin/sh
# 在容器中执行：
while true; do wget -q -O- http://myapp; done

# 5. 观察 HPA 自动扩容
watch kubectl get hpa,pod
```

- **效果**：CPU 使用率超过 50% 时自动扩容，低于目标时自动缩容

**场景 4：基于自定义指标的伸缩**

- **痛点**：CPU 使用率不能反映实际业务负载
- **方案**：基于 QPS 或延迟进行伸缩

**具体实现：**
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: myapp-hpa-custom
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: myapp
  minReplicas: 2
  maxReplicas: 20
  metrics:
    # 自定义指标：每秒请求数
    - type: Pods
      pods:
        metric:
          name: http_requests_per_second
        target:
          type: AverageValue
          averageValue: "1000"  # 目标：每个 Pod 处理 1000 QPS
    
    # 自定义指标：延迟
    - type: Pods
      pods:
        metric:
          name: http_request_latency_seconds
        target:
          type: AverageValue
          averageValue: "0.1"   # 目标：平均延迟低于 100ms
    
    # 保留 CPU 作为备用指标
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 70
```

**暴露自定义指标（使用 Prometheus Adapter）**：
```yaml
# prometheus-adapter-configmap.yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: prometheus-adapter-config
  namespace: kube-system
data:
  config.yaml: |
    rules:
      # QPS 指标
      - seriesQuery: 'http_requests_total'
        resources:
          overrides:
            namespace: {resource: "namespace"}
            pod: {resource: "pod"}
        name:
          matches: "http_requests_total"
          as: "http_requests_per_second"
        metricsQuery: 'sum(rate(http_requests_total{<<.LabelMatchers>>}[1m])) by (<<.GroupBy>>)'
      
      # 延迟指标
      - seriesQuery: 'http_request_duration_seconds_bucket'
        resources:
          overrides:
            namespace: {resource: "namespace"}
            pod: {resource: "pod"}
        name:
          matches: "http_request_duration_seconds_bucket"
          as: "http_request_latency_seconds"
        metricsQuery: 'histogram_quantile(0.5, sum(rate(http_request_duration_seconds_bucket{<<.LabelMatchers>>}[1m])) by (le,<<.GroupBy>>))'
```

**应用端暴露指标**（Go + Prometheus）：
```go
package main

import (
    "net/http"
    "github.com/prometheus/client_golang/prometheus"
    "github.com/prometheus/client_golang/prometheus/promhttp"
)

var (
    httpRequestsTotal = prometheus.NewCounterVec(
        prometheus.CounterOpts{
            Name: "http_requests_total",
            Help: "Total number of HTTP requests",
        },
        []string{"method", "path", "status"},
    )

    httpDuration = prometheus.NewHistogramVec(
        prometheus.HistogramOpts{
            Name:    "http_request_duration_seconds",
            Help:    "HTTP request latency",
            Buckets: prometheus.DefBuckets,
        },
        []string{"method", "path"},
    )
)

func init() {
    prometheus.MustRegister(httpRequestsTotal)
    prometheus.MustRegister(httpDuration)
}

func main() {
    http.HandleFunc("/", func(w http.ResponseWriter, r *http.Request) {
        start := time.Now()
        
        // 业务逻辑
        w.WriteHeader(http.StatusOK)
        w.Write([]byte("Hello"))
        
        // 记录指标
        duration := time.Since(start).Seconds()
        httpDuration.WithLabelValues(r.Method, r.Path()).Observe(duration)
        httpRequestsTotal.WithLabelValues(r.Method, r.Path(), "200").Inc()
    })

    // 暴露 metrics 端点
    http.Handle("/metrics", promhttp.Handler())
    
    http.ListenAndServe(":8080", nil)
}
```

- **效果**：根据实际业务负载（QPS、延迟）自动伸缩

## ⚖️ 优缺点分析

| 维度 | ✅ 优点 | ❌ 缺点/局限性 |
|------|---------|---------------|
| **健康检查** | 自动发现故障、减少MTTR | 配置不当可能导致频繁重启 |
| **优雅停止** | 零宕机更新、数据一致性 | 需要应用支持信号处理 |
| **水平伸缩** | 自动适应负载变化 | 冷启动延迟、成本控制 |
| **垂直伸缩** | 优化资源利用 | 需要 Pod 重启 |
| **成本效益** | 提高资源利用率 | 复杂度增加 |
| **可观测性** | 与监控告警集成 | 需要额外配置 |
